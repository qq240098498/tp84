# tp84 依赖台账与版本核查平台

一个本地小工具：把各个项目用到的依赖集中登记起来。页面上先建项目，再往项目下面登记依赖名称、版本、许可、责任人与状态；同一个依赖被两个项目用到时，版本高低一眼能比出来。依赖名写得不合规矩、版本不是三段数字、同一个项目里重复登记同一个依赖，保存时当场就会指出来。

责任人视图按人统计每个人名下压着多少条依赖，展开能看到具体是哪些项目的哪些依赖；没写责任人的单独归在一组。转交可以批量做：勾选一批登记后先预演会改动哪些条目、前后条数怎么变，确认再执行，每次转交都留下什么时候由谁转给谁的记录；把责任人改成空的按撤掉责任人处理，这些登记会回到没人负责的那一组。

数据全部存在本机的数据文件里，不连数据库，也不调用任何外部服务。

## 技术栈

- 后端：Node.js（>=18）与 Express，前后端同一个进程
- 前端：原生 HTML、CSS 与 JavaScript，页面文件由后端静态目录直接提供，没有构建步骤
- 存储：本地 JSON 文件 `data/db.json`

## 启动方式

```bash
npm install
npm start
```

启动后打开页面地址：<http://localhost:5084>

端口固定为 `5084`，如需临时改动可在启动前设置环境变量 `PORT`。

## 页面怎么用

1. 顶栏右侧可以填当前操作者，填过之后浏览器会记住，新建登记时会把它带进责任人
2. 项目区列出项目名称、负责人、说明与这个项目下已经登记了多少条依赖；可以新增项目，也可以改名、换负责人、删除
3. 依赖登记区顶部可以按项目、状态、许可筛选，再按依赖名、责任人或者备注搜索，右上角刷新按钮重新拉取一次
4. 点新建登记，选好所属项目，填上依赖名称、版本，按需要补许可、责任人、状态与备注；列表里点编辑会把这条登记回填到表单
5. 任何一步不成立时，页面顶部给出说明，并尽量把问题标到对应的输入项上；删除项目与删除登记都会先确认
6. 责任人区按人列出每个人名下的依赖条数，点展开能看到具体是哪些项目的哪些依赖；没写责任人的单独归在未指定一组，最后一行是合计，方便对数
7. 批量转交：在展开的分组里勾选登记（表头的勾选框可以全选这一组），填新责任人或勾选撤掉责任人，先点预演看会改动哪些登记、前后条数怎么变，确认后才真正执行；执行后原责任人名下不再留着转走的条目，新责任人名下把转进来的条目算上
8. 转交记录区按时间列出每次转交：什么时候、由谁（取顶栏填的当前操作者，没填记成未留名）、转给了谁、一共多少条，展开能看到每一条登记原来的责任人；撤掉责任人的转交也记在这里，新责任人显示为未指定

项目下面还挂着依赖登记时不允许删除项目，页面上会写清还剩多少条、例如哪几条，先处理这些登记再删。

## 登记口径

- 依赖名称以小写字母或数字开头，可以用小写字母、数字、点、下划线、短横线与斜线，最长 60 个字符；带范围的写法例如 `@types/node` 也按这个口径登记
- 版本写成三段数字，例如 `2.7.18`，需要时可以带一段预发布后缀，例如 `5.0.10-rc.1`
- 许可按实际名称填写，例如 `MIT`、`Apache-2.0`、`BSD-3-Clause`；还没确认的可以留空，列表里会显示成未填
- 责任人可以留空，表示这条依赖还没有定人
- 状态只有三种：在用、待升、已弃用
- 备注用来写为什么用这个版本、有没有待办，最长 200 个字符
- 同一个项目下不允许出现同名的依赖，同一个依赖在不同项目里各登记各的、互不覆盖

## 数据存储

所有数据写在 `data/db.json`，结构为 `{ "projects": [...], "deps": [...], "transfers": [...] }`。`transfers` 是转交留痕：每次转交涉及时的时间、操作者、新责任人与每一条登记原来的责任人都会记下来，登记以后被删掉也不影响已经留下的记录。落盘时先把内容写进同名临时文件，再用改名的方式替换正式文件，写入过程中断也不会把数据文件写坏；文件缺失或内容损坏时会自动回落到初始数据。

## 接口一览

| 方法   | 路径                     | 说明                                                         |
| ------ | ------------------------ | ------------------------------------------------------------ |
| GET    | /api/health              | 服务状态检查                                                 |
| GET    | /api/projects            | 项目清单，附带每个项目的依赖条数                             |
| POST   | /api/projects            | 新增项目                                                     |
| PATCH  | /api/projects/:id        | 修改项目的名称、负责人或说明                                 |
| DELETE | /api/projects/:id        | 删除项目                                                     |
| GET    | /api/deps                | 依赖登记列表，支持按项目、状态、许可筛选与关键词搜索         |
| POST   | /api/deps                | 新增依赖登记                                                 |
| GET    | /api/deps/:id            | 查看单条依赖登记                                             |
| PATCH  | /api/deps/:id            | 修改依赖登记                                                 |
| DELETE | /api/deps/:id            | 删除依赖登记                                                 |
| GET    | /api/owners              | 按责任人分组的依赖条数与明细，没写责任人的单独一组           |
| GET    | /api/transfers           | 转交记录，新的在前                                           |
| POST   | /api/transfers/preview   | 批量转交预演：只算不改，返回会改动哪些登记与前后条数对照     |
| POST   | /api/transfers           | 批量转交执行：新责任人留空按撤掉责任人处理，并留下转交记录   |

转交类接口的请求体为 `{ "depIds": ["..."], "toOwner": "...", "operator": "..." }`（预演不需要 `operator`）。`toOwner` 为空串表示撤掉责任人，这些登记回到未指定一组。

接口出错时统一返回 `{ "error": { "code": "...", "message": "...", "field": "..." } }`，其中 `field` 用于让页面把问题标到具体的输入项上。
